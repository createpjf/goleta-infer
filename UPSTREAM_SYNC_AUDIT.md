## TL;DR — verdict

**The Task 1.2 strategy in the plan ("sync to upstream llama.cpp main via `git merge`") is structurally broken and must be replaced.**

PowerInfer's fork is not "a slightly-behind llama.cpp." It contains **three different llama.cpp lineages**, two embedded inside the same repo, and none of them is recent enough to support Qwen 3.5. A merge-and-resolve workflow doesn't make sense — what's needed is a base reset.

## 4. Three options to replace plan §1.2 ("git merge upstream main")

### Option α — Base reset to `llamacpp/master`, re-apply ggml-mlx on top (recommended)

Discard PowerInfer's entire fork structure. Treat `goleta-infer` as a fresh fork of `ggerganov/llama.cpp`, with our ggml-mlx work re-applied as a small set of clean commits.

```bash
# On phase1-qwen35 branch
git checkout llamacpp/master -- .                          # Take all of upstream
git checkout HEAD~3 -- ggml-mlx.h ggml-mlx.c MLXKernels.swift mlx-spike/  # Re-apply our work
# Adapt CMakeLists.txt + Package.swift to upstream's modular layout
git add -A && git commit -m "phase1: reset base to llama.cpp main, re-apply ggml-mlx backend"
```

**Cost:** 1-2 days to re-apply ggml-mlx work in the new modular layout (the C interface is the same; just file paths change).

**Pros:**
- Inherits Qwen 3.5 support immediately
- Clean modern repo structure
- Future upstream syncs are normal `git pull llamacpp master` operations
- ~340k lines of PowerInfer-only vendor code (perfetto, gtest, etc.) are deleted — much smaller repo

**Cons:**
- Loses PowerInfer's sparse-activation code paths. (Already not used per Path 3a, so this is actually a feature.)
- Repo description "fork of Tiiny-AI/PowerInfer" becomes inaccurate; should re-describe as "fork of ggerganov/llama.cpp."
- Existing branches `phase0-mlx-stub`, `phase0-mlx-spike`, `phase1-qwen35` reference top-level files that won't exist in this layout. Must rebase or recreate.

### Option β — Adapt Package.swift to `smallthinker/`, sync only that subtree

Use PowerInfer's embedded `smallthinker/` llama.cpp clone (9 months behind) as the base, sync it to current upstream via subtree merge or manual file replacement, leave top-level rotting.

**Cost:** 3-5 days. Same merge complexity (smallthinker is itself far from upstream), plus Package.swift surgery to change all source paths.

**Pros:** Keeps PowerInfer's `powerinfer/libaz/` sparse-activation code accessible (in case sparse ever becomes relevant again).

**Cons:** Repo has two abandoned directories at root. Mental model harder for any future contributor.

### Option γ — Abandon Path X, pivot to Path Y

Drop the goleta-infer fork. Use Apple's `mlx-swift-examples` for Qwen 3.5 9B inference, written as Swift wrapper around mlx-vlm.

**Cost:** 1.5–2 weeks (per pre-Phase-0 analysis).

**Pros:** No fork maintenance burden. Apple keeps the inference loop fresh.

**Cons:** Tied to mlx-swift-examples' supported model list. Cannot easily add custom kernels later.

## 5. Risks identified

- **R-A1 (new):** PowerInfer's sparse-activation code in `powerinfer/libaz/` is the only thing distinguishing this fork from a llama.cpp fork. Path 3a doesn't use it. If the user wants to keep it accessible "just in case," that's option β — but it costs structural complexity for code we've benchmarked as a regression on Apple Silicon.
- **R-A2:** Re-applying our Phase 0 ggml-mlx work in option α requires understanding upstream's new ggml backend abstraction (`ggml-backend-impl.h` has been refactored). Estimate 1 day of orientation work.
- **R-A3:** `unsloth/Qwen3.5-9B-GGUF` was generated against upstream llama.cpp's `convert_hf_to_gguf.py`. If our final code uses some non-upstream loader or PowerInfer-modified arch table, the file may not load. Option α eliminates this risk; options β/γ should verify.
- **R-A4 (resolved by α):** PowerInfer's repo carries ~340k lines of vendor trees (perfetto, fmt, gtest) that aren't part of our use case but bloat clone time and CI build matrix.

---

## Recommendation to controller

**Take option α.** The data invalidates the original Task 1.2 merge plan. PowerInfer's fork is not a viable base for chasing modern llama.cpp; it's effectively three abandoned llama.cpp lineages held together by build files. The PowerInfer-specific value (sparse activation) is dead code on Apple Silicon per the Phase 0 spike.

Option α takes ~1-2 days of well-defined work and leaves us with a clean fork of current llama.cpp + our ggml-mlx backend. That is what Path X actually needs to be — the original plan's "merge" framing was wrong because it assumed PowerInfer's fork structure was sound. It isn't.

If the user wants to preserve the "fork of PowerInfer" framing for narrative reasons (e.g. external comms about goleta-infer's lineage), option β is the fallback at higher engineering cost.

If the user wants to escape Path X entirely, option γ is on the table — but the user has rejected this twice now in earlier rounds.
